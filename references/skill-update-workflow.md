# `tech-doc-reviewer` Skill 升级流程（AgentBuddy 分发版）

本文是通过 AgentBuddy 分发的 `tech-doc-reviewer` Skill 的升级流程。当用户提出“检查更新”“升级 Skill”“拉取最新规范”或同类请求时，按本文执行。

> AgentBuddy 分发链接：<https://skills.bytedance.net/skill/skills:code.byted.org/tongyuting/aime-skills/tech-doc-reviewer>

## 1. 适用范围与核心原则

### 1.1 适用范围

本流程适用于通过上述 AgentBuddy 链接安装或订阅 `tech-doc-reviewer` 的用户。该场景下：

- Skill 的发布源由作者维护，AgentBuddy 负责从 Codebase 仓库同步并分发；
- 普通用户不需要访问底层 Codebase 仓库；
- 普通用户不需要提供 Personal Access Token（PAT）；
- 升级单元是 AgentBuddy 分发的完整 Skill 包，而不是单独覆盖 `SKILL.md` 或 `CHANGELOG.md`。

### 1.2 核心原则

1. **AgentBuddy 是普通用户的升级入口**：版本发现、下载和完整包同步均通过 AgentBuddy 完成。
2. **不向普通用户索取 Codebase Token**：不得要求用户提供 `read_repository` Token，也不得引导用户手动执行 Git 拉取。
3. **先检测、后确认、再升级**：发现新版本后，先展示版本和变更摘要；用户明确确认后再执行会改变本地状态的升级。
4. **完整包原子替换**：不得只更新单个文件，也不得混用当前版本与新版本中的 `references/`、`scripts/` 等文件。
5. **以实际可验证结果为准**：仅在版本、目录完整性和基础校验均通过后，才可宣称升级成功。
6. **不猜测 AgentBuddy 接口**：只使用当前运行环境已提供并有明确说明的 AgentBuddy 安装、更新或重新同步能力；若当前环境无法直接执行，应引导用户打开分发链接完成升级，不得臆造 CLI、API 或参数。

## 2. 角色与版本来源

| 对象 | 职责 | 权威信息 |
|---|---|---|
| Skill 作者 | 在 Codebase 仓库中维护并推送新版本 | `main` 分支中 `tech-doc-reviewer/` 的完整目录 |
| AgentBuddy | 自动同步源仓库，并向用户分发可安装的最新 Skill 包 | AgentBuddy 分发页展示或返回的版本与完整包 |
| 用户当前环境 | 保存当前已安装或当前草稿版本 | 本地 `SKILL.md` frontmatter 中的 `metadata.version` |
| CHANGELOG | 说明版本间的行为和规则变化 | 当前包与目标包中的 `references/CHANGELOG.md` |

版本比较时：

- **当前版本**：读取当前环境中 `tech-doc-reviewer/SKILL.md` frontmatter 的 `metadata.version`；
- **最新版本**：读取 AgentBuddy 分发页或 AgentBuddy 官方安装/更新能力返回的版本信息；
- **目标版本内容**：以 AgentBuddy 实际分发的完整包为准；
- **历史变更**：以目标包中的 `references/CHANGELOG.md` 为准。

若任一版本号缺失、格式无法解析，或 AgentBuddy 未提供可核验的最新版本信息，不得推测版本关系，应停止自动升级并说明待核验项。

## 3. 升级触发方式

### 3.1 用户主动触发

用户可使用以下任一自然语言请求发起升级：

- “检查 `tech-doc-reviewer` 是否有新版本。”
- “把 `tech-doc-reviewer` 升级到 AgentBuddy 最新版。”
- “从 AgentBuddy 拉取最新规范。”
- “更新技术文档评审 Skill。”

收到请求后，先确认目标 Skill 为 `tech-doc-reviewer`，再进入版本检测。用户无需提供仓库地址、分支、Token 或 Git 凭据。

### 3.2 仅检查，不执行升级

若用户只要求“查看版本”或“检查更新”，默认只执行版本检测并展示结果，不改变本地文件或安装状态。只有用户明确表达“升级”“更新”“同步”等执行意图后，才进入升级确认和执行阶段。

### 3.3 指定版本

若 AgentBuddy 支持选择历史版本，用户可以指定目标版本。执行前必须确认：

- 目标版本在 AgentBuddy 中真实存在；
- 目标版本不低于当前版本，除非用户明确要求降级；
- 降级可能丢失新规则或破坏兼容性，必须单独提示风险并再次确认。

若 AgentBuddy 仅分发最新版，则不得声称可以安装指定历史版本。

## 4. 版本检测

### 4.1 读取当前版本

1. 定位当前环境中的 `tech-doc-reviewer` Skill 根目录。
2. 读取 `SKILL.md` frontmatter 中的 `metadata.version`。
3. 记录当前版本号，不修改任何文件。

若当前环境不存在该 Skill，应将本次请求按“首次安装”处理，并明确告知用户“当前未安装，将安装 AgentBuddy 最新版”。

### 4.2 查询 AgentBuddy 最新版本

通过 AgentBuddy 分发链接或当前环境已提供的 AgentBuddy 官方能力，读取以下信息：

- Skill 名称；
- 最新版本号；
- 更新时间；
- 可用的变更说明或目标包 `CHANGELOG`；
- 分发源标识，确认目标确实是 `tongyuting/aime-skills/tech-doc-reviewer`。

不得通过底层 Codebase raw URL、用户 Token 或手工 Git 拉取代替此步骤。

### 4.3 比较版本

按结构化版本号比较当前版本与 AgentBuddy 最新版本，不得仅按字符串字典序比较。处理结果如下：

| 检测结果 | 处理方式 |
|---|---|
| 当前版本低于最新版本 | 展示版本差异和变更摘要，等待用户确认升级 |
| 当前版本等于最新版本 | 回复“当前已是 AgentBuddy 最新版本 `<版本号>`，无需升级” |
| 当前版本高于最新版本 | 提示当前环境可能是未发布草稿、预发布版或 AgentBuddy 尚未完成同步；不得自动覆盖 |
| 版本号缺失或不可解析 | 停止自动升级，说明无法可靠判断版本关系 |
| AgentBuddy 页面不可访问或未返回版本 | 说明当前无法完成在线版本检测，保留现有版本 |

### 4.4 展示升级摘要

检测到新版本后，至少向用户展示：

- 当前版本；
- AgentBuddy 最新版本；
- 两个版本之间的变更摘要；
- 可能影响现有工作流的兼容性变化；
- 确认问题：“是否升级到 `<目标版本>`？”

如果 AgentBuddy 未提供完整变更记录，应明确标注“变更摘要不可用”，不得自行编造；用户仍可选择继续升级完整包。

## 5. 升级执行

### 5.1 前置检查

升级前依次检查：

1. 用户已明确确认升级；
2. 目标来源为指定的 AgentBuddy 分发链接；
3. 当前 Skill 是否存在未提交、未上传或未废弃的本地草稿；
4. 当前环境是否提供受支持的 AgentBuddy 更新、重新安装或重新同步能力。

若存在本地草稿，必须暂停升级并提示：直接同步 AgentBuddy 版本可能覆盖本地修改。用户需要先选择以下一种处理方式：

- 保留并上传草稿，使其成为新的受管版本；
- 导出或提交本地修改后再升级；
- 明确放弃草稿，再恢复 AgentBuddy 自动同步。

未经用户确认，不得自动删除或覆盖草稿。

### 5.2 自动升级路径

当当前环境提供明确的 AgentBuddy 更新或重新同步能力时：

1. 使用分发链接识别目标 Skill；
2. 请求同步 AgentBuddy 最新完整包；
3. 由 AgentBuddy 或当前 Skill 管理能力完成完整目录替换；
4. 保证 `SKILL.md`、`.skillignore`、`references/`、`scripts/` 和其他受管文件来自同一目标版本；
5. 等待同步返回明确成功结果；
6. 进入升级后验证。

不得把“已打开分发页”“已触发下载”或“命令已启动”视为升级成功。

### 5.3 用户操作路径

若当前环境不能直接调用 AgentBuddy 更新能力，应执行以下降级路径：

1. 向用户提供 AgentBuddy 分发链接；
2. 引导用户在分发页执行“更新”“重新安装”或页面实际提供的等价操作；
3. 不要求用户填写 Codebase 仓库、分支或 Token；
4. 用户完成页面操作后，重新读取当前环境中的 Skill 版本并执行验证。

只有在回读确认目标版本已生效后，才可回复升级成功；若无法回读，应说明“AgentBuddy 侧操作已发起，但当前环境尚未确认版本生效”。

### 5.4 首次安装路径

当前环境未安装 `tech-doc-reviewer` 时：

1. 通过 AgentBuddy 分发链接安装最新完整包；
2. 安装完成后读取 `metadata.version`；
3. 执行与升级相同的完整性和基础校验；
4. 明确回复“已安装”，不要使用“已升级”。

## 6. 压缩包离线安装用户的迁移升级

本章适用于曾通过 ZIP、tar.gz 等压缩包手工解压并离线安装 `tech-doc-reviewer` 的用户。此类安装通常没有 AgentBuddy 分发绑定关系，不能假设会自动收到后续版本。

### 6.1 识别离线安装

满足以下任一条件时，按离线安装路径处理：

- 用户明确说明此前通过压缩包安装；
- 当前 Skill 可以读取，但无法确认 AgentBuddy 分发源；
- 当前 Skill 没有受管来源或自动同步信息；
- 本地目录由用户手工复制、解压或覆盖生成。

“无法确认来源”不等于一定是离线安装。若证据不足，应先询问用户原安装方式，不得直接覆盖。

### 6.2 迁移原则

离线安装用户升级时，不再下载新的压缩包手工覆盖，而是迁移到 AgentBuddy 分发版本。迁移完成后，后续检查更新和升级统一走本文的 AgentBuddy 流程。

迁移必须遵守以下原则：

1. **先识别本地修改**：检查当前目录是否包含用户自行修改的规则、脚本或引用文件。
2. **先备份、后替换**：存在本地修改或无法判断时，先完整备份原 Skill 目录。
3. **完整包替换**：不得将 AgentBuddy 新文件直接叠加到旧压缩包目录，避免已删除文件残留或跨版本混用。
4. **不继承来源不明的改动**：未经用户确认，不把旧压缩包中的自定义内容自动合并到 AgentBuddy 版本。
5. **迁移后建立分发关系**：最终安装结果必须能够识别为 AgentBuddy 分发的 `tech-doc-reviewer`，而不是另一个手工目录副本。

### 6.3 读取和判断旧版本

1. 定位离线安装的 Skill 根目录。
2. 读取旧目录中 `SKILL.md` 的 `metadata.version`。
3. 读取旧目录中的 `references/CHANGELOG.md`（若存在）。
4. 记录旧版本号、目录位置和来源状态。
5. 检查是否存在以下本地修改：
   - 文件内容与旧版本基线不一致；
   - 新增的 `references/`、`scripts/` 或其他文件；
   - 用户明确说明曾修改规则；
   - 无法通过版本信息确认目录是否保持原样。

若旧压缩包没有 `metadata.version`，记录为“旧版本未知”。不得因无法识别旧版本而阻止迁移，但必须跳过版本差异结论，并明确提示无法生成完整的跨版本变更摘要。

### 6.4 迁移前确认

向用户展示：

- 当前安装方式：压缩包离线安装；
- 当前版本或“版本未知”；
- AgentBuddy 目标版本；
- 是否发现或疑似存在本地修改；
- 迁移影响：原离线目录将被 AgentBuddy 完整包替换，后续升级改走 AgentBuddy；
- 备份位置或拟采用的备份方式；
- 确认问题：“是否迁移并升级到 AgentBuddy `<目标版本>`？”

用户明确确认前，不得删除、覆盖或停用原离线安装。

### 6.5 无本地修改时的迁移步骤

确认旧目录未包含本地修改后：

1. 记录旧版本和目录位置；
2. 通过指定的 AgentBuddy 分发链接安装最新完整包；
3. 确认 AgentBuddy 安装已成功写入当前环境；
4. 移除或停用旧的离线副本，避免出现两个同名 Skill；
5. 按“升级后验证”章节完成版本、来源、目录完整性、结构和最小功能验证。

只有 AgentBuddy 版本验证通过后，才能清理旧副本。若安装或验证失败，应继续保留旧版本，不得使用户处于无可用 Skill 的状态。

### 6.6 存在本地修改时的迁移步骤

检测到或疑似存在本地修改时：

1. 完整备份旧 Skill 目录，并记录旧版本；
2. 生成本地修改清单，至少列出新增、修改和删除的文件；
3. 向用户说明本地修改不会自动继承，并让用户选择：
   - **仅迁移官方版本**：保留备份，安装 AgentBuddy 最新版，不合并本地修改；
   - **迁移后重新应用修改**：先安装 AgentBuddy 最新版，再把确认仍适用的修改逐项重做为本地草稿；
   - **暂不迁移**：继续保留离线版本，但不承诺自动更新。
4. 用户选择“迁移后重新应用修改”时，必须先完成 AgentBuddy 安装和验证，再按 Skill 草稿编辑流程逐项迁移；不得直接复制整个旧目录覆盖新版本。
5. 重新应用修改后，应再次执行结构校验和最小功能验证。

重新应用的本地修改属于新的草稿，会暂停 AgentBuddy 自动同步。必须明确提醒用户：只有上传或废弃草稿、退出草稿状态后，才会恢复受管版本同步。

### 6.7 重名目录和双版本处理

如果离线版本与 AgentBuddy 版本同时存在：

- 不得保留两个可被运行时同时加载的同名 `tech-doc-reviewer`；
- 先确认 AgentBuddy 版本验证通过，再停用、移走或删除旧离线副本；
- 备份目录不得放在会被 Skill 扫描或加载的位置；
- 无法判断运行时实际加载哪个版本时，升级状态应标记为“未完成”。

### 6.8 迁移成功标准与提醒

同时满足以下条件，才可宣称迁移升级成功：

- 本地回读版本与 AgentBuddy 目标版本一致；
- 分发源能够确认指向指定 AgentBuddy Skill；
- 旧离线副本不再参与运行；
- 目录完整性、结构和最小功能验证通过；
- 旧版本或本地修改已按用户选择完成备份或迁移。

建议回复：

> 已将 `tech-doc-reviewer` 从压缩包离线安装迁移到 AgentBuddy `<目标版本>`。旧版本已按约定备份或停用，当前运行版本、分发来源和目录完整性已验证。后续可直接通过 AgentBuddy 检查和获取更新，无需再次下载压缩包或提供 Codebase Token。

## 7. 升级后验证

升级完成后必须执行以下检查。

### 7.1 版本验证

- 重新读取本地 `SKILL.md` 的 `metadata.version`；
- 确认其与本次 AgentBuddy 目标版本一致；
- 若不一致，判定升级未完成，不得宣称成功。

### 7.2 来源验证

确认当前 Skill 对应的分发源仍为：

`skills:code.byted.org/tongyuting/aime-skills/tech-doc-reviewer`

若无法核验来源，明确标注“来源未核验”；若来源不一致，停止使用该结果并提示用户检查安装目标。

### 7.3 目录完整性验证

至少检查：

- `SKILL.md` 存在且 frontmatter 可解析；
- `.skillignore` 存在；
- `references/CHANGELOG.md` 存在；
- `SKILL.md` 中引用的本地文件均存在；
- `references/`、`scripts/` 等目录没有因单文件覆盖而形成跨版本混用；
- 目标包中已删除的受管文件未继续残留并参与运行。

### 7.4 结构校验

若当前环境提供 Skill 校验能力，运行 `quick_validate.py` 或等价官方校验；同时检查 Markdown 相对链接。若校验工具不可用，应明确列出已完成的静态检查，不得伪称“完整校验通过”。

### 7.5 最小功能验证

在不修改业务数据的前提下，验证：

- Skill 可以被正常加载；
- “检查更新”“评审技术文档”等典型触发意图仍能路由到该 Skill；
- `metadata.version` 与 `CHANGELOG` 最新条目一致；
- 核心引用文件可读取。

验证失败时，保留错误信息并明确告知用户。不得以旧版本部分可用为由宣称新版本升级成功。

## 8. 完成提醒

### 8.1 升级成功

建议回复：

> `tech-doc-reviewer` 已通过 AgentBuddy 从 `<当前版本>` 升级到 `<目标版本>`。已完成版本、来源、目录完整性和基础结构校验。后续 AgentBuddy 发布新版本时，可再次发起“检查更新”或“升级 Skill”。

### 8.2 已是最新版

固定回复：

> 当前已是 AgentBuddy 最新版本 `<版本号>`，无需升级。

### 8.3 升级未完成

回复中必须包含：

- 当前版本；
- 目标版本；
- 失败阶段；
- 具体错误或未核验项；
- 当前版本是否仍可使用；
- 用户下一步需要执行的操作。

不得在版本未回读一致、校验失败或同步状态不明确时使用“升级成功”。

## 9. 与旧流程的关系

### 9.1 默认关系：替换普通用户升级流程

对于通过 AgentBuddy 分发链接安装或使用 `tech-doc-reviewer` 的普通用户，本流程**完全替换**以下旧步骤：

- 用户提供 `read_repository` PAT Token；
- 使用 `PRIVATE-TOKEN` 请求 Codebase raw 文件；
- 用户手动执行 Git 拉取或目录复制；
- 升级后要求用户到 Skill 管理页再次 Publish 才能使用。

AgentBuddy 场景下，上述步骤不再向普通用户暴露，也不应作为失败后的默认降级方案。

### 9.2 旧流程保留边界

旧的 Codebase/Git 流程仅在以下维护者场景独立保留，不属于普通用户升级：

- Skill 作者修改源仓库内容；
- 作者在 Codebase 提交、合并或回滚版本；
- 作者验证 AgentBuddy 是否已同步仓库最新提交；
- AgentBuddy 分发链路故障时，由维护者进行源仓库诊断。

维护者流程与用户升级流程必须分开成独立章节或独立文档，避免普通用户误以为升级必须提供 Token。

### 9.3 路由判定

| 场景 | 使用流程 |
|---|---|
| 用户通过 AgentBuddy 链接安装，要求检查或升级 | 本文的 AgentBuddy 升级流程 |
| 用户只想获取最新版，不关心底层仓库 | 本文的 AgentBuddy 升级流程 |
| 用户曾通过压缩包离线安装 | 先按第 6 章迁移到 AgentBuddy，再使用常规升级流程 |
| 作者要修改、提交或回滚源 Skill | Codebase/Git 维护者流程 |
| 用户明确使用自有仓库维护私有分支 | 独立的自有仓库同步流程；不得冒充 AgentBuddy 升级 |
| 当前存在本地草稿 | 先处理草稿冲突，再恢复 AgentBuddy 同步或执行升级 |
| AgentBuddy 暂不可用 | 停止普通用户升级并说明原因；不得回退为索取 Token |

## 10. 异常与回滚

### 10.1 常见异常

| 异常 | 处理方式 |
|---|---|
| AgentBuddy 无法访问 | 保留当前版本，稍后重试；不索取 Codebase Token |
| AgentBuddy 显示版本与本地一致，但内容不同 | 标记分发一致性异常，停止自动覆盖并记录版本、更新时间和文件差异 |
| 本地版本高于 AgentBuddy | 视为草稿、预发布或同步延迟，禁止自动降级 |
| 存在本地草稿 | 暂停自动同步，先让用户选择保留、上传或放弃草稿 |
| 完整性校验失败 | 判定升级失败；不要仅恢复某一个文件形成混合版本 |
| 升级后无法加载 | 优先使用 Skill 管理能力恢复上一完整可用版本；无法自动恢复时保留诊断信息并告知用户 |

### 10.2 回滚要求

回滚必须以“上一完整可用版本”为单位，不得只回滚 `SKILL.md`。若 AgentBuddy 不支持选择历史版本，应明确说明当前无法自助回滚，并由维护者在分发源修复或重新发布可用版本。

## 11. 安全与审计要求

- 全流程不得要求、接收、记录或持久化用户 Codebase Token；
- 不读取或修改与 `tech-doc-reviewer` 无关的 Skill；
- 不通过未公开、未验证的 AgentBuddy API 或命令绕过分发机制；
- 记录版本检测和升级结果时，仅记录版本号、时间、来源标识和验证结果，不记录用户凭据；
- 涉及覆盖本地草稿、降级或回滚时，必须先获得用户明确确认。

## 12. 推荐落地方式

建议直接用本文替换现有 `references/skill-update-workflow.md`，并将作者侧的 Codebase 操作另存为“维护者发布流程”。同时检查 `SKILL.md` 中“版本与升级”章节，确保其仍指向本文，并补充以下路由说明：

替换后应同步检查：

6. 通过完整包同步、回读版本和结构校验构成升级成功标准。
