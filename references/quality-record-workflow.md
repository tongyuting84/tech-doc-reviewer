# 质检记录写入流程

完成正式评审报告并交付给使用者后，将本次发现的每一条问题写入指定飞书多维表格，用于二次质检与修复率追踪。该步骤不得跳过；写入失败时必须明确报错并说明原因。

## 目标

- 多维表格：https://bytedance.larkoffice.com/base/NFbaboIHEaL92hsS5UYc8BDonEe
- 数据表名称：**质检记录**

## 写入粒度

- 一条问题写入一行；N 条问题写入 N 行。
- 不写入 P0/P1/P2 数量、问题总计等汇总字段。
- 不将问题详情组织为 JSON 数组。
- 没有发现问题时不写入记录。

## 字段映射

| 字段 | 取值规则 |
|---|---|
| 质检日期 | 评审当天日期。必须调用 calendar 或 truetime 类时间工具获取，不得自行推算或手写。 |
| 使用人 | 当前发起评审请求的用户名。 |
| 文档标题 | 被评审文档的标题。 |
| 文档 URL | 被评审文档链接；本地文本或对话内文本没有 URL 时留空。 |
| 问题等级 | 本条问题级别，单选值为 `P0`、`P1` 或 `P2`。 |
| 原文描述 | 对应的原文锚定片段，建议不超过 30 个字。 |
| 问题详情 | 按“【问题描述】……\n\n【修改建议】……”组织为多行文本。 |
| 是否修复 | 首次质检不提交该字段；二次质检时回填“是”或“否”。 |
| 二次质检 | 首次质检不提交该字段；二次质检完成后回填“是”。 |

## 执行步骤

1. 使用 `managing-lark-bitable-data` skill 解析 Base URL，获取真实 `base_token`。
2. 获取“质检记录”数据表的真实 `table_id`，并读取字段结构。
3. 确认上述字段存在、类型匹配；确认“问题等级”的选项包含 `P0`、`P1`、`P2`。
4. 将每条问题映射为独立记录，只提交首次质检允许写入的字段。
5. 使用 [write_quality_records.py](../scripts/write_quality_records.py) 进行 payload 校验、分批和串行写入。单批最多 200 条。
6. 以写入返回结果确认成功；失败时停止并向使用者说明错误，不得修改或删除已有记录。

## 脚本输入

脚本读取一个 JSON 文件，格式如下：

```json
{
  "create_records": [
    {
      "质检日期": "2026-10-12",
      "使用人": "tongyuting",
      "文档标题": "示例文档",
      "文档 URL": "https://example.com/doc",
      "问题等级": "P1",
      "原文描述": "示例原文",
      "问题详情": "【问题描述】……\n\n【修改建议】……"
    }
  ]
}
```

不要在首次质检 payload 中包含“是否修复”或“二次质检”。先使用脚本的默认 dry-run 检查；确认参数后追加 `--apply` 执行真实写入。
